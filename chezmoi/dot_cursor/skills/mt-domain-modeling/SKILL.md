# ドメインモデリング

設計中にプロジェクトのドメインモデルを能動的に構築・鋭化する。これは*能動的な*規律である — 用語に異議を唱え、エッジケースのシナリオを発明し、用語集と決定が結晶化した瞬間に書き留める。（`CONTEXT.md` を語彙として*読む*だけではこの Skill ではない — それはどの Skill でもできる 1 行の習慣に過ぎない。この Skill はモデルを*変更する*時に使うのであり、単に消費する時ではない。）

## ファイル構成

ほとんどのリポジトリは単一文脈:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` が存在する場合、そのリポジトリは複数文脈を持つ。マップが各文脈の所在を指す:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体の決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 文脈固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延作成する — 書くものができた時だけ作る。`CONTEXT.md` が存在しなければ、最初の用語が確定した時点で作成する。`docs/adr/` が存在しなければ、最初の ADR が必要になった時点で作成する。

## セッション中

### 用語集に照らして異議を唱える

ユーザーが `CONTEXT.md` の既存言語と衝突する用語を使った場合、即座に指摘する。「用語集では 'cancellation' は X と定義されていますが、Y の意味で使っているようです — どちらですか？」

### 曖昧な言語を鋭化する

ユーザーが曖昧な語や過積載な語を使った場合、正確な正規用語を提案する。「'account' と言っていますが — Customer のことですか、User のことですか？これらは別のものです。」

### 具体的なシナリオで議論する

ドメインの関係性が議論されている時、具体的なシナリオでストレステストする。エッジケースを probe し、概念間の境界についてユーザーに正確さを求めるシナリオを発明する。

### コードと突合する

ユーザーが何かの仕組みを述べた時、コードがそれに同意するか確認する。矛盾を見つけたら表面化させる。「コードは Order を丸ごとキャンセルしていますが、先ほど部分キャンセルが可能と言いました — どちらが正しいですか？」

### CONTEXT.md をその場で更新する

用語が確定したら、その場で `CONTEXT.md` を更新する。まとめて後で書こうとしない — 起きた瞬間に記録する。形式は [CONTEXT-FORMAT.md](CONTEXT-FORMAT.md) に従う。

`CONTEXT.md` には実装詳細を一切書かない。`CONTEXT.md` を仕様書、スクラッチパッド、実装判断の置き場として扱わない。これは用語集であり、それ以外ではない。

### ADR は絞って提案する

次の 3 つをすべて満たす場合のみ ADR の作成を提案する:

1. **覆すコストが高い** — 後から考えを変えるコストが意味のあるもの
2. **文脈なしでは驚かれる** — 将来の読み手が「なぜこうした？」と疑問に思う
3. **実在するトレードオフの結果** — 本物の代替案があり、具体的な理由で選んだ

3 つのうち 1 つでも欠けたら ADR は作らない。形式は [ADR-FORMAT.md](ADR-FORMAT.md) に従う。
