# Gherkin 形式

`.feature` は `features/` に置き、機能単位で 1 ファイルにする。

## 慣習の推論

書き方はリポジトリの既存 `.feature` から推論する — キーワード言語、ファイル命名、説明の有無、シナリオの粒度、ステップの言い回し。値（シナリオ名・ステップ文言・説明）の言語は日本語に固定する。既存がなければ以下を既定とする。

## 配置と命名

- **配置**: 既定はリポジトリ直下の `features/`。既存の `.feature` が別の場所にあれば、その配置に従う。
- **拡張子**: 常に `.feature`。
- **ファイル名**: kebab-case の機能名（`ordering.feature`、`save.feature`）。
- **分割**: 既存ファイルの機能領域に属するシナリオは追記する。新しい領域は新規ファイルを作り、`Feature:` で始める。
- **インデント**: 2 スペース。シナリオ配下のステップは 4 スペース。既存に合わせる。

## キーワード

- キーワードの既定は英語。既存 `.feature` が日本語キーワードなら、それに合わせる。
- 値（シナリオ名・ステップ文言・説明）は日本語で書く。

| 英語 | 日本語 |
| --- | --- |
| Feature | 機能 |
| Background | 背景 |
| Scenario | シナリオ |
| Scenario Outline | シナリオアウトライン |
| Examples | 例 |
| Given | 前提 |
| When | もし |
| Then | ならば |
| And | かつ |
| But | しかし |

## シナリオの粒度

- **1 シナリオ 1 振る舞い。** 複数の振る舞いを 1 シナリオに詰めない。
- **Given は状態、When は操作、Then は観測可能な結果。** 内部実装（テスト ID、DOM 構造、関数名）をステップ文言に持ち込まない。
- **具体値で書く。** 抽象的な「正しい値」ではなく、具体例で振る舞いを固定する。
- **Background は全シナリオに共通する前提だけ。** 分岐する前提を Background に押し込まない。
- **Scenario Outline は入力の組み合わせが本質の時だけ。** 1 つの振る舞いを複数例で示す必要がなければ普通のシナリオにする。

## 語彙

- CONTEXT.md の正規語だけを使う。`_Avoid_` の語は使わない。
- シナリオに新しい語が必要なら、先に CONTEXT.md を更新してから書く。

## ステップ文言

- 既存ステップと同じ意味は同じ文言を使う。同じ意味のステップを増やすとステップ定義が重複する。
- パラメータは既存の書き方（`{string}` 等）に合わせ、リテラルを埋め込まない。
- 対応するステップ定義がない文言は一覧にして申し送る。ステップ定義は書かず、テストも実行しない。

## 既存 `.feature` の語彙揺れ

シナリオ名・コメント・データ文字列・新規に書く部分の揺れは正規語に直す。ステップ文言はステップ定義に結合しているため変更せず、修正案の提示に留める。

## 例

```gherkin
Feature: 定時同期
  Scenario: リモートの変更が取り込まれる
    Given Vault "octocat/notes" が同期済みである
    When リモートのノート "daily/2026-08-08.md" が変更されている
    Then ローカルのノート "daily/2026-08-08.md" に変更が取り込まれる
```
