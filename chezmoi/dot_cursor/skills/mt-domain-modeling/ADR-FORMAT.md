# ADR 形式

ADR は `docs/adr/` に配置し、連番を使う: `0001-slug.md`、`0002-slug.md` など。

`docs/adr/` ディレクトリは遅延作成する — 最初の ADR が必要になった時だけ作る。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3 文: 文脈は何か、何を決定したか、なぜか。}
```

これだけでよい。ADR は 1 段落でよい。価値は*決定が行われた*ことと*その理由*を記録することにあり — セクションを埋めることではない。

## 任意セクション

純粋に価値を加える場合のみ含める。ほとんどの ADR には不要。

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 決定が再訪される時に有用
- **Considered Options** — 却下した代替案を覚えておく価値がある時だけ
- **Consequences** — 自明でない下流の影響を明示する必要がある時だけ

## 連番

`docs/adr/` をスキャンして既存の最大番号を見つけ、1 を加算する。

## ADR を提案する条件

次の 3 つをすべて満たす必要がある:

1. **覆すコストが高い** — 後から考えを変えるコストが意味のあるもの
2. **文脈なしでは驚かれる** — 将来の読み手がコードを見て「なぜこんなことを？」と思う
3. **実在するトレードオフの結果** — 本物の代替案があり、具体的な理由で選んだ

決定が容易に覆せるなら、飛ばす — どうせ覆す。驚かれないなら、誰も理由を疑問に思わない。本物の代替案がなかったなら、「自明なことをした」以上に記録することはない。

### 何が該当するか

- **アーキテクチャの形状。** 「モノレポを使う。」「ライトモデルはイベントソーシング、リードモデルは Postgres へ射影。」
- **文脈間の統合パターン。** 「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する。」
- **ロックインを伴う技術選択。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではない — 入れ替えに四半期かかるものだけ。
- **境界とスコープの決定。** 「顧客データは Customer 文脈が所有; 他の文脈は ID でのみ参照。」明示的な No は Yes と同じくらい価値がある。
- **自明なパスからの意図的な逸脱。** 「ORM の代わりに手書き SQL を使う。理由は X。」合理的な読み手が逆を想定するようなもの。次のエンジニアが意図的なものを「修正」するのを防ぐ。
- **コードから見えない制約。** 「コンプライアンス要件で AWS は使えない。」「パートナー API 契約でレスポンスは 200ms 以内でなければならない。」
- **却下が自明でない代替案。** GraphQL を検討して REST を選んだ理由が微妙なら、記録する — さもないと半年後に誰かがまた GraphQL を提案する。
