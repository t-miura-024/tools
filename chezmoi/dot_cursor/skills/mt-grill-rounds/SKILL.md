# 指示

共通の認識に達するまで、ユーザーに徹底的に質問を投げかけ続ける。これを**設計ツリー**（design tree）として地図化する: すべての決定は、その決定にぶら下がる決定群へと枝分かれする。

ツリーは**ラウンド**（round）単位で進める。**フロンティア**（frontier）とは、前提条件がすべて確定済みの決定 — まだ聞いていない回答を推測することなく、*今この瞬間*に尋ねられる質問の集合である。1 ラウンドではフロンティア全体を必ず尋ねる（質問数に上限は設けない）: 各質問に番号を付け、推奨回答を添える。そして次のラウンドに進む前に、ユーザーの回答を待つ。

## 質問フォーマット

各質問は次のフォーマットで提示する:

```
**Q1** - **<質問タイトル>**: <質問本文。複数段落になってもよい>

1. <選択肢 1> — ★★★★★ <理由>
2. <選択肢 2> — ★★★☆☆ <理由>
3. <選択肢 3> — ★☆☆☆☆ <理由>

推奨回答: <最も推奨する選択肢の番号>
```

- AskQuestion / AskUserQuestion ツールは使わず、質問の本文内で番号付きの選択肢を必ず 3 つ提示する
- 各選択肢に 5 段階の推奨度と理由を添える。推奨度は左から黒星で表示する（1 点は ★☆☆☆☆、4 点は ★★★★☆）
- 自然な候補が 3 つに満たない場合も、自由記述・その他・保留などの具体的な第 3 案を作る
- 末尾の「推奨回答」で、あなたが最も推奨する選択肢の番号を明示する

各ラウンドでユーザーが回答するたびに、ツリーは再構成される — 確定した決定がフロンティアを外側へ押し出し、その決定に依存していた質問のブロックが外れる。フロンティアを再計算し、次のラウンドを尋ねる。このラウンドでまだ未決の別の質問の回答に依存する質問は、今回のラウンドではなく*後の*ラウンドに属する。

*事実*を見つけるのはあなたの仕事であり、ユーザーの仕事ではない。フロンティアの質問が環境（ファイルシステム、ツール等）からの事実を必要とする場合、SubAgent を派遣して調査させる — 自分で調べられることをユーザーに聞いてはならない。ただし、調査の完了を待ってブロックしない: 進行中の調査は未確定の前提条件であり、その下流にある質問だけが SubAgent の報告を待つ — フロンティアの残りの質問は、今すぐ尋ねる。*決定*はユーザーのものだ — 一つひとつ提示して、回答を待つ。

## ライブ地図（grill-map.md）

設計ツリーは、ライブ地図 `grill-map.md` としてセッション中に育て続ける。

- 既定パスは `tmp/mt-grill-rounds/grill-map.md`。呼び出し元がパスを指定した場合は、そちらを優先する（例: `mt-create-plan` workflow は `tmp/tado/<id>/grill-map.md` を指定する）
- 地図は Markdown で構造化する。構造や深さは固定せず、議論対象と決定間の依存関係に応じて適応的に決める
- 地図では Why（なぜ取り組むか）/ What（何を決めるか）/ How（どう実現するか）を漏れなく扱う。ただし、これらを固定の見出しとして強制せず、議論対象に適した構造へ組み込む
- 決定事項・未決定事項・保留事項を区別し、セッション中を通して継続的に記録する。表現方法は地図の構造に合わせて選ぶ
- 各ラウンドの回答を反映した後・次のラウンドを提示する前に、地図を更新する
- 質疑ログは残さず、回答から得た決定とその理由、残った未決定事項や保留事項をライブ地図へ蒸留し続ける

## mt-domain-modeling 併用時

mt-domain-modeling と併用する場合、確定用語と ADR 案を地図の適切な位置へ組み込み、ドメインモデルと同期させる。用語が確定した瞬間や ADR 案が浮かんだ瞬間に記録し、まとめて後で書こうとしない。

## 終了条件

フロンティアが空になった時、セッションは完了する: 設計ツリーのすべての枝を訪れ、暗黙のまま前提として残したものが何もない状態である。ただし、共通認識に達したことをユーザーが確認するまで、実行に移さない。
