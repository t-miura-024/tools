# 検証観点プールを Tier 制で管理し width/depth で制御する

## 背景 (Context)

敵対的検証の観点は当初、マクロ/ミクロ/共通の 3 分類や `mt-sdd-*` の 9 分割など、観点の粒度と重複が不統一であった。全観点を常に適用すると低 effort でも過剰な指摘が発生し、逆に個別呼び出しでは観点選択が属人的になる課題があった。検証強度を段階制御する手段として、再現可能な決定論的写像が求められた。

旧 `mt-sdd-*` はエッジケース・重複・抽象的ロジック観点など、テストや他観点に内包できるものが含まれており、15 観点への正規化が必要であった。width（広さ）と depth（深さ）の 2 軸で強度を表現し、grill で「depth は担当観点数で定義し、プロンプトの広さを拡張しない」方針が合意された。

## 決定 (Decision)

差分の敵対的検証観点 15 観点を 4 カテゴリ・5 ティアで管理し、width は累積ティア制（low=4〜max=15）、depth は担当観点数（max 1:1〜low 1:all）で制御することとした。決定論的な写像により effort の 5 段階が再現可能になり、観点ごとの専念度と検証強度を段階制御できる。

- カテゴリ: 要件(2) / ロジック(4) / AI アンチパターン(4) / アーキテクチャ(5) の 4 分類、計 15 観点。
- Tier: T1 最優先(4 観点: 要件-1, 要件-2, ロジック-1, AI-1)〜T5(1 観点: アーキ-5) の 5 段階。優先度で累積する。
- width: low=T1(4) / medium=T1+2(8) / high=T1+2+3(12) / xhigh=T1+2+3+4(14) / max=全(15)。配列スライスで決定論的に算出する。
- depth: max 1:1 / xhigh 1:2 / high 1:3 / medium 1:4 / low 1:all。並列数は `⌈採用観点数 ÷ 担当観点数⌉` で導出し、最大 6/波で波分割する。
- 削除・統合の経緯: エッジケースはテスト委譲で廃止、重複・抽象度は分離/凝集/結合へ内包、ライブラリ選定・認知負荷は削除、抽象的ロジック観点は分解。

検証者 SubAgent `mt-review-diff-reviewer` は担当観点のみを指摘し、担当外は指摘しないスコープ規律と、攻撃者・利用者・保守者の敵対視点で反証するスタンスを持つ。

## 代替案 (Considered Options)

- 動的 LLM 選択で観点を都度選定する方式: LLM の判断で観点が変動し、width の再現性が担保できない。effort の 5 段階を決定論的に再現する要件に反するため不採用。
- フラットな 15 観点リストを width で単純に先頭から N 個取る方式: 優先度が反映されず、低 width で重要観点が漏れる可能性がある。Tier 制の累積制の方が優先度を明示できると判断し不採用。
- 観点数を増やし 20 以上で細分化する方式: 検証コストと SubAgent 並列数が増大し、tracer bullet の最小構成を超える。15 観点が現行の Issue 要求とテスト委譲のバランスで最適と判断し見送り。
- depth をプロンプトの文字数や詳細度で定義する方式: プロンプト長と検証深度の相関が不明確で、depth の体感を定量化できない。担当観点数という明確な指標で専念度を制御する方が運用しやすいため不採用。

## 帰結 (Consequences)

- width と depth の決定論的写像により、`width=high depth=medium` 等の指定で再現可能な検証強度が得られる。`tado init` のパラメータ機構不在でも、プロンプト記法（`width=… depth=…`）と human_gate のハイブリッドで effort を解決できる。
- 低 width では T1 のみが適用され、最重要の目的整合・仕様カバレッジ・エラーハンドリング・ハルシネーションチェックに絞った高速検証が可能。高 width では全観点で網羅的な敵対的検証が行える。
- depth による波分割（最大 6/波）で並列実行が制御され、観点ごとの専念度が担保される。max では 1:1 で最も深い検証が行える。
- 観点プールは `mt-review-diff` ワークフロー内で SoT として管理され、観点の追加・Tier 変更は単一箇所で完結する。テストは Tier 配列のスライスと並列数計算の純粋関数で担保する。
